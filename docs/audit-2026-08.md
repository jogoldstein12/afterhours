# After Hours — Holistic App Audit

**Date:** August 26, 2026
**Scope:** Functionality, UX, UI, content deck, code quality, infrastructure.
**Context:** Internal development phase, used by a small group of friends. Security explicitly out of scope for this audit.
**Method:** Full source read, production build + typecheck + lint run, live app booted and exercised with Playwright (mobile + desktop viewports), full 890-prompt deck review, standalone `game.html` diffed against the deck.

---

## Verdict

The app is in better shape than most first-audit projects: the visual identity is coherent and confident, the core pass-the-phone loop works, the standalone `game.html` is genuinely offline-capable and byte-identical in content to the main deck, and the production build passes. The biggest problems are not in what was built but in what was turned off, duplicated, or left half-connected: every quality gate is disabled, the PWA layer is broken in ways that 404 on every page load, the game logic exists twice and has already drifted, and the prompt deck — the actual product — has heavy duplication, inverted difficulty, and a handful of prompts with real consent problems.

**Scorecard**

| Area | Grade | One-liner |
|---|---|---|
| Visual design / UI | B+ | Coherent neon identity; a few mobile layout and redundancy issues |
| Core gameplay | B− | Works, but has a deck-reset bug, unfair turn order, and no skip/undo |
| Content deck | C | 890 prompts but 60+ duplicate clusters, tier miscalibration, consent outliers |
| Code quality | C+ | Clean components, but gates off, dead deps, duplicated game engine |
| PWA / offline | D | Registration 404s, white manifest, unmaintained plugin, unverified offline |
| Infra / tooling | D+ | No CI, no lint config, no tests, no monitoring; hosting itself is fine for this phase |

## 1. Red flags

These are the things I'd want fixed or decided before inviting anyone beyond the friend group.

### 1.1 Every quality gate is off
`next.config.ts` sets `typescript.ignoreBuildErrors: true` and `eslint.ignoreDuringBuilds: true`. ESLint has **never been configured** — `npm run lint` drops into the first-run setup wizard. There are zero tests and no CI. The build output literally prints "Skipping validation of types / Skipping linting."

The good news: turning the gates back on is nearly free right now. The only current typecheck error is a missing type declaration for `next-pwa` (a one-line `declare module 'next-pwa'` shim fixes it). This is the cheapest moment the project will ever have to flip these on; every week of development with gates off raises the price.

### 1.2 The PWA layer is broken and misleading
- `src/app/layout.tsx:38` loads `/register-sw.js`, **which does not exist** — a 404 fires on every page load of every route (confirmed live). `next-pwa` with `register: true` injects its own registration anyway, so the tag is at best dead weight and at worst a sign the SW setup was never verified.
- `public/manifest.json` sets `theme_color` and `background_color` to `#ffffff` — a white splash/status chrome on a near-black neon app.
- The manifest points both icon entries (192 and 512) at the same `After_Hours_App_Icon.png`, while the purpose-built `icon-192x192.png` / `icon-512x512.png` sit unused next to it. No maskable icon.
- `next.config.ts` has a `runtimeCaching` rule for `/api/prompts` — an endpoint that doesn't exist.
- `next-pwa@5.6` is unmaintained (last release 2022) and predates Next 15 / the app router. If offline PWA is a real requirement, migrate to a maintained equivalent (e.g. `@serwist/next`) and actually test install + airplane mode. If it isn't — the standalone `game.html` already covers offline — consider deleting the PWA layer entirely rather than shipping a broken one.

### 1.3 Adding or removing a player mid-game silently resets the deck
`src/app/game/page.tsx:102-107` — the effect that reloads prompts depends on `players.length`, so any roster change through Manage Group wipes `usedPromptIds` and deals a fresh deck. An hour into a game, adding a latecomer erases all progress with no warning. (The standalone `game.html` does *not* do this — one of several behavioral drifts between the two implementations.)

### 1.4 Fonts are loaded twice, two different ways
`layout.tsx` self-hosts Inter and Space Grotesk via `next/font` **and** loads the same two families again from a manual Google Fonts `<link>`. Double download, external dependency that defeats offline, and a layout-shift risk. Delete the manual `<link>` block (lines 32-34); `next/font` alone is strictly better.

### 1.5 Consent and calibration problems in the deck
Security may be out of scope, but content safety is the product's actual risk surface for a party game:

- **id 187** — "biggest boobs must allow everyone to feel them" — mandates group physical contact with no opt-out. This is the worst offender and should be removed or rewritten with a drink-out alternative.
- Several forced-contact prompts (182, 199, 200, and the Extreme touch/strip clusters) have no escape hatch because **the app has no Skip button** — the roadmap doc already flags this as the top "do first" item and it's still missing. A skip-with-penalty is the single mechanic that makes the entire Extreme tier safe to play.
- **id 243** asks for STI disclosure — sensitive health information as a party forfeit.
- Tier misfiling: a large batch of hard-Extreme content sits in Medium (anal 141, orgy 152, public masturbation 163, groping 187, choking 263, stripping 210-215, showing nudes 189/224), while some Extreme entries are tame (306 "most embarrassing thing on your phone"). Duplicate prompts even carry contradictory tiers: 161 (Medium) and 322 (Extreme) are the same "sex outdoors" prompt.
- **The drink economy is inverted.** Medium hands out 8-12 drink penalties; Extreme never exceeds 5 and has essentially zero give-out mechanics. Medium is objectively the drunkest mode.
- **NHIE mode mixes all tiers with no filter** — 80 of its 125 prompts are Extreme. A group choosing "Never Have I Ever" expecting something tamer than Extreme gets Extreme content immediately, with no signal on the setup screen.

### 1.6 The deck is one-third duplicates
890 prompts, but the content audit found **60+ duplicate or near-duplicate clusters** — some with five to eight variants of the same idea (body count ×6, lap dance ×8, body shots ×7, "sex in a car" ×3, "faked an orgasm" ×5, private-room ×6...). Effective unique content is far below the headline number, and players will notice repeats within a single long session since duplicates aren't linked (using one doesn't retire its twins).

### 1.7 The game engine exists twice and has already drifted
The Next.js app and `tools/standalone-template.html` each implement the full game logic independently. They already disagree on: deck-reset on roster change (1.3 above), what happens when you re-tap the current level (standalone silently resets the deck — a real bug), remove-player index semantics, and used-prompt tracking keys. Every gameplay change now has to be made twice and tested twice, and nothing checks they stay in sync. `tools/build-standalone-html.js` also only works by accident: its slice captures `[] = [...]` (a destructuring expression) rather than the array literal, and it has latent `String.replace('$…')` and `</script>`-injection hazards. Worth a small refactor: emit the deck as JSON and share one game-logic module between both targets.

### 1.8 Documentation and data that lie
- `docs/prompts.csv` claims to be the deck spreadsheet but is stale: 613 rows vs 890 prompts, missing the entire 900-1176 batch, and contains duplicated ids 246-259 from a pre-renumbering era. Regenerate it from `prompts.ts` in the build script, or delete it.
- `README.md` advertises "Player & Gender-Specific Prompts: the game supports prompts that can be targeted based on player gender" — **no such feature exists.** Meanwhile 6 prompts (186, 187, 222, 240, 241, 242) actually do depend on gender the app never collects.
- The AI moderation feature (Genkit flow + `/moderator-test` page) is disconnected from gameplay — nothing feeds it, its output goes nowhere, the required Gemini API key is undocumented (no `.env.example`), and the internal test page ships in the production bundle. Decide: wire it into a real custom-prompts feature, or cut it and drop the genkit dependencies (which also emit handlebars warnings in every build).

## 3. UX findings

**Setup screen**
- Levels are chosen blind — no description of what Mild/Medium/Extreme mean, and the difference is dramatic. (Roadmap §1.1, 15-minute fix, still open.)
- **NHIE gives no hint that it spans all spice levels** including Extreme. This needs a label or, better, a spice sub-filter.
- Start button is always enabled and error-toasts on failure instead of being disabled with a hint (roadmap §1.3).
- Players re-type names every single session — no localStorage memory (roadmap §1.6). For a repeat-play friend group this is the most-felt papercut.

**Game screen**
- Mobile header is cramped: the logo is squeezed between the player name and the count, the wordmark wraps to two lines, and a long player name will collide with it. The absolutely-positioned `scale-[0.6]` logo hack (flagged in roadmap §4.4) is the cause.
- "# OF PLAYERS" badge above "3 PLAYERS" text says the same thing twice; that header slot could show something useful (round number, prompts remaining).
- An accidental tap on "Next Player" is unrecoverable — no undo, no back, and the prompt is retired forever. In a pass-the-phone game mis-taps are constant.
- No skip (see 1.5), no drink tally, no timer for the many "for 30 seconds" prompts — the top three items on your own roadmap, all still open.
- **The screen sleeps mid-game.** A pass-the-phone game should hold a wake lock (`navigator.wakeLock`) while a card is showing.
- "End Game" opens a dialog titled "Start a New Session?" with a red "New Game" button — red signals destructive, and the label/title/button vocabulary doesn't match ("End" vs "Start" vs "New").
- Deck exhaustion ("Last Call!") is abrupt — no stats, no recap, no celebration (roadmap §2.5).

**Accessibility**
- New prompts are not announced — the card needs `aria-live="polite"` for screen readers.
- Multiple text elements at 50-60% white opacity on near-black are below WCAG AA contrast.
- Continuous smoke/neon animations have no `prefers-reduced-motion` fallback.

## 4. UI / visual

The neon identity is genuinely good — consistent palette, committed dark theme, the mode-colored card borders (violet/pink/red) are a nice touch of information-in-form. Issues:

- White flash risk on load: PWA chrome uses the white manifest colors (1.2).
- `globals.css` defines `.text-secondary`, overriding Tailwind's own utility of the same name — a collision waiting to confuse someone.
- `@apply dark` inside `body` styles (globals.css:91) is a no-op hack; dark mode is already forced via the `html` class. The duplicated `:root` / `.dark` token blocks are pure copy-paste weight.
- The dead `Header` nav placeholder (`{/* ... existing navigation buttons ... */}`) ships in the component.

## 5. Code quality & repo hygiene

- **Dead dependencies:** `firebase` (the entire client SDK) is a dependency and is imported nowhere. `patch-package` is installed with no `patches/` directory. `recharts`, `react-day-picker`, `date-fns`, `react-hook-form`/`zod` (forms) are used only by unused shadcn components.
- **24 of 33 shadcn components are unused** (accordion, avatar, calendar, chart, sidebar, table, tabs…). They don't bloat the client bundle (tree-shaken) but they bloat maintenance, installs, and audits like this one.
- `page.tsx:36` mutates state objects in place (`newPlayers[index].name = name`) and player rows use `key={index}` — both work today, both are the classic source of future subtle bugs.
- `game/page.tsx:111` sets a "Game Over!" message that is never rendered (the "Last Call!" block renders instead).
- `game.html` (141KB generated artifact) is committed at the root. It **is** currently in sync with the deck — but only convention keeps it that way. A CI check (`npm run build:html && git diff --exit-code game.html`) would make staleness impossible.
- No `CLAUDE.md`/CONTRIBUTING; the README's install section still says `git clone <your-repository-url>`.

## 6. Infrastructure

- **Hosting:** Firebase App Hosting (`apphosting.yaml`, `maxInstances: 1`) — fine for the friends phase. Worth knowing: the app is **fully static** (every route prerenders; the only server-side code is the unused moderation action). If moderation is cut or moved, this could be `output: 'export'` and hosted on any static host — simpler and free. Not deployed on your Vercel or Railway accounts (checked both).
- **No CI whatsoever** — no `.github/`, nothing runs on push. Minimum viable pipeline: typecheck, lint, build, `game.html` freshness check. Half a day of work, permanent payoff.
- **No error monitoring and no analytics** — you have no way to know if the app crashes at a party or which levels people actually play (roadmap §5.4).
- **No `.env.example`** — the Gemini key requirement for the moderation flow is undiscoverable.
- Toolchain pins are healthy: Node 20 (nix), Next 15.3.8, React 18, lockfile committed. `next-pwa` is the one rotten dependency (1.2).

## 7. What's working well

Credit where due — these should be preserved through any refactor:

- The standalone `game.html` is a genuinely great artifact: fully offline, zero dependencies, XSS-safe (all user text via `textContent`), graceful font fallback, and byte-identical prompt content to the main deck.
- The NHIE mode design — a regex-derived virtual tier rather than a fourth content silo — is clean and means NHIE prompts never fork from their home tiers.
- The visual identity is distinctive and consistently executed across both implementations.
- The existing `afterhours_ux_improvements.md` roadmap is honest and well-prioritized. Its "Do First" list (level descriptions, skip button, disabled start, typo fixes) is validated by this audit — the issue is only that none of it has been implemented yet.
- `docs/blueprint.md` shows the original scope; the core of it (setup → randomizer → pass-the-phone → filter) is fully delivered.
